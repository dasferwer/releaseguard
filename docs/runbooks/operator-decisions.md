# Почему релиз находится в этом состоянии

Читайте `GET /api/v1/releases/{id}` и `/events` с ключом известного клиента.
`state_reason` поясняет последнее решение; журнал хранит причину перехода,
actor и исходные данные. При создании релиза решение ещё не принято: первый
подписанный результат CI запускает оценку обязательных проверок.

| Состояние | Что проверить / следующее действие |
|---|---|
| `evaluating` | `release.gates_evaluated`: `required_gates`, `results` и названные в reason отсутствующие проверки. Дождаться CI, не согласовывать заранее. |
| `blocked` | Проваленные обязательные проверки названы в reason. Окружение освобождено; исправить артефакт и создать новый релиз. Поздний webhook не возобновляет старый. |
| `awaiting_approval` | Все CI gates пройдены; `requires_approval=true`. Отдельный approver вызывает `/approve`. |
| `approved` | В reason указан автоматический допуск или ручное согласование; `/deploy` ещё раз проверит gates под lock. |
| `canary` | Начато наблюдение; `canary.observed` хранит данные, thresholds, decision и reason. Малый объём запросов даёт continue; превышение любого порога сразу rollback, даже при малом объёме. |
| `succeeded` | Число запросов достаточно, error_rate и p95 не превышают порогов. Значение точно на пороге разрешено. |
| `rolled_back` | Причина различает превышение конкретных порогов, ручной откат и timeout. При timeout смотреть `canary.timeout` и источник метрик. |
| `cancelled` | Причина оператора записана; повтор cancel не создаёт нового события и не освобождает блокировку следующего релиза. После canary используется rollback. |

`release.gates_evaluated` сохраняется при каждом принятом результате CI, включая
случай без перехода состояния. Идентичный повтор webhook не создаёт новый snapshot;
запрос, отклонённый до фиксации, не попадает в журнал решения. Результаты CI
после закрытия их приёма получают 409. Исторические события старых версий не
дополняются задним числом.

Пороги canary сохраняются именно в момент наблюдения. Timeout и ручной rollback
не являются подтверждением плохой метрики. Окончательные решения и `traffic_percent`
относятся к модели в PostgreSQL: ReleaseGuard не переключает ingress/трафик,
не разворачивает пользовательское приложение и не подтверждает его восстановление.

## Воспроизводимые сценарии

`scripts/operator_scenarios.py` создаёт собственные объекты через обычный API,
проверяет пять сценариев и печатает их фактические releases/events:

```sh
RELEASEGUARD_SMOKE_URL=http://127.0.0.1:8091 python -m scripts.operator_scenarios
```

Запускайте на своём демонстрационном стенде с работающим reconciler и
`CANARY_TIMEOUT_SECONDS=30`; при обычном timeout=300 последний сценарий намеренно
не дождётся отката за свой ограниченный срок 90 секунд. Ключи/secret задаются
через те же `RELEASEGUARD_*` переменные, что у `scripts/smoke.py`.
Сценарии: недостаточный объём→успешная canary→ручной rollback; провал CI и
отклонение позднего webhook; cancel и повтор; превышение обоих порогов при
малом объёме; отсутствие метрик и настоящий reconciler timeout.

JSON содержит состояния модели и журнал, не результаты реального переключения
трафика. Сервис не имеет отдельного frontend: проверка API/journal является
операторской проверкой, browser UI/E2E здесь не заявляется.
